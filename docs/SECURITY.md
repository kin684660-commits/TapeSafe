# 安全边界与威胁模型

本项目未接受独立审计。测试覆盖是开发证据，不是资金安全保证。

## 本版本的约束

- 阈值必须小于成员数，必签掩码不能要求全部成员，避免发起人不计票引起的全局死锁。必签人数可以大于最低门槛：门槛是下限，不是最多批准人数。
- 冻结会增加配置版本，旧批准立即失效。禁止在未冻结时预先创建解冻提案，以减少预签解冻绕过应急响应的机会。
- 配置提案目标必须为执行器，金额必须为零；解除冻结 calldata 必须是准确的 4 字节选择器。
- NFT 接收钩子只接受指定合约和 vaultId。执行前核验 NFT 与容器所有者。
- 执行函数有重入锁；仅暴露 CALL，不提供 delegatecall 或 NFT 转出入口。
- 交易费用精确匹配，且不得超过 MAX_FEE；失败回滚执行状态。

## 仍需信任的部分

- TapeOut 的 factory、circuits/container beacon 及其升级管理员。若 eval 被升级成恒真，执行器不能提供独立的策略安全保证。
- NFT 永久托管不可撤回。错误电路、错误容器、签名人失联和全部必签人无法配合，均可能导致资产不可恢复。
- 单个签名人可以反复冻结造成拒绝服务，这是应急权限的显式权衡。
- CALL 可以调用危险合约、ERC-20 approve 或转移其他资产；“没有 delegatecall”不意味着任意 calldata 安全。
- 两 RPC 一致不保证它们独立或诚实；同高度模拟到最终上链之间存在竞争，钱包和 RPC 也可能失效。
- 本地 release 清单无可信引导，不构成反篡改保证。采用 DeWEB 时仍需验证网关、引导代码及协议管理员的信任边界。
- 处理器与电路的归属关系、链上网表与仓库的字节一致性，需结合实际创建/流片交易收据验证。

## 未涵盖

独立审计、形式化验证、所有代币语义兼容性、完整生产监控、密钥恢复和资产迁移。部署前应根据计划演示的实际调用补测。
